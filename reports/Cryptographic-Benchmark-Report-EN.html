4. Experimental method

Windows. The benchmark ran on Windows 11 on an Intel Core i7-12700H with Java 25.0.1. Each algorithm and input size used one JVM, three warm-up encrypt–decrypt pairs and five successive batches targeting at least three seconds each. The benchmark recorded separate monotonic encryption and decryption durations and checked plaintext recovery. PowerJoular 2.0.0-beta-1 sampled CPU package power approximately once per second. Energy is the sum of watts multiplied by the overlap between each power interval and the batch. Dividing by the actual pair count yields J/pair. PowerJoular release

Android. An IV2201 ran three warm-up pairs and 100 measured pairs per batch. Ebserver orchestrated each batch over wireless ADB. The standard battery service reported Not charging while unplugged. A device-specific probe sampled raw voltage and current from /sys/class/power_supply/battery/uevent about every 500 ms plus ADB overhead. The calculation assumes mV and mA and uses trapezoidal integration. At least four valid samples and an unplugged state are required. Units have not been independently calibrated, and the window can include instrumentation startup, warm-up and teardown. The dataset includes both foreground and background conditions.

5. Ebserver operation and source code

Ebserver is the Node.js orchestration component of UserEnergy. The project-specific src/crypto.js adapter reads a JSON matrix, verifies the handset, resets diagnostic statistics, invokes AndroidJUnitRunner over ADB, collects timing and battery files, and records each outcome in execution.csv. Desktop benchmarking uses the JVM runner and PowerJoular.

  1. Enable wireless debugging on the phone. Pair using the pairing dialog, then connect using the address on the main wireless debugging page. Confirm the wireless device is listed as device.
  2. Build and install the application and instrumentation APKs. Unplug the phone and check that all power-source flags are false.
  3. From the Ebserver directory, validate the JSON with --dry-run, then run the pilot before starting a full matrix. In the configuration, powers are byte exponents, so 11 is 2 KiB and 20 is 1,024 KiB.
  4. Review the manifest, ledger, batch CSVs and raw probe traces. Resume with the original device, configuration and run directory. Successful batch keys are retained.

6. Interpretation and reproducibility

  • Five batches support descriptive means and sample standard deviations. Windows batches within a case share one JVM and are not independent process restarts.
  • Windows energy includes background CPU activity. Android energy includes background battery load, instrumentation and sampling overhead. Neither workflow resolves separate energy for encryption and decryption.
  • Some Android batches were retried after OS freezing or wireless disconnection. Retain the logged execution conditions when interpreting energy. The large-size Android results contain the completed eight-algorithm matrix, including all five GIFT-COFB repeats at 1 MiB.
  • Algorithm modes and authentication properties differ. RSA and ElGamal are hybrid schemes that wrap the AES key and IV. Timings describe the measured implementations and do not establish security equivalence.
